# Ashes of Empires, Loop Lessons

Living memory for the Muse takeover build loop (started 2026-10-15, Jash's order). Read at the start of every run. Append at the end of every run: what failed and why, what pattern worked, what to try or avoid next time. If a lesson proves wrong, strike it through with a dated note instead of deleting it.

## Lessons

- 2026-10-15, reconciliation discovery: the GitHub branch state in the takeover brief (about 10 ahead, 4 behind) was stale by the time the first takeover run checked it. The branch claude/adoring-johnson-cf5bmq is in fact 136 commits ahead of remote master and 0 behind, because it was rebased onto master's Cycle 6 step 5 commit and then kept building through Cycles 7 to 17 on 2026-10-13 and 2026-10-14. Lesson: never trust a brief's branch counts. Measure the branch with the compare API at the start of reconciliation and log the measured counts.
- 2026-10-15, gh.py path bug: the GitHub fetch script inserts a wrong sys.path (templates/skill/bin) and fails with ModuleNotFoundError for dynamic_credentials on a plain run. Setting PYTHONPATH to /opt/muse/skills/custom-connector-setup/bin makes the exact script named in the mission work without editing it. Use that prefix for every gh.py call in this loop.
- 2026-10-15, port in authored slice order, but assess before replacing: the branch's first reconciliation slice added a balance harness, but master gained its own committed harness in Cycle 6 step 5 (commit 797b1b8) that reproduces the verified step 4 numbers. Overwriting it blindly would have traded a verified harness for an unverified one. Diff before treating a branch item as unique, exactly as the mission warned for tools/balance.js.
- 2026-10-15, test-only slices are the safest first port: the drawn in defender reversal test (slice 2) applied as a pure append, passed on master unchanged (40 of 40), and changed no balance numbers. When a reconciliation contains a test that pins a behavior master already claims, port the test early; it turns a claimed behavior into a pinned one.
- 2026-10-15, a branch harness that gates on profiles that fail is information, not a defect to hide: the branch slice 1 harness records that its no factory script loses seed 31337 and its factory path won only 1 of 8 on the pre slice sim. Those failures are what slices 4 (research clock) and 5 (lines paid before factories) were built to fix. Do not port the gating harness before the sim slices it depends on, or the repo will carry a red gate with no fix in the same step.
- 2026-10-15, gh.py fetch is not idempotent over a dirty destination: a leftover extracted directory in /tmp/ashes-gh-sync made the fetch fail with a rename Directory not empty error partway through, leaving a half synced copy that looked like a real diff. Lesson: rm -rf /tmp/ashes-gh-sync before every fetch, and never trust a diff from a fetch that exited non-zero.
- 2026-10-15, branch commit patches are fetchable one at a time through the GitHub commits API with the same surrogate credential gh.py uses: GET /repos/jashshah854-a11y/ashes-game/commits/<sha> returns the full per file patch. That is the clean way to port one authored slice verbatim without fetching the whole 136 commit branch.
- 2026-10-15, reconciliation step 3: a branch patch authored in slice order still applies verbatim after master has diverged by its own port commits (compare now reads 136 ahead, 2 behind; the 2 behind are the slice 2 and slice 3 port commits). Check fidelity by matching the local diff stat against the branch patch's per file counts (slice 4: sim 12 insertions and 2 deletions, test 16 insertions) before running tests.
- 2026-10-15, a timing parity fix can leave every standard balance band identical and still be real: slice 4 changed no number in master's harness output, and its effect is pinned only by its dedicated research clock test. Do not judge a slice by whether the balance table moved.
- 2026-10-15, do not import branch balance claims for profiles master's harness does not run: the branch slice 4 message quotes sensible without factories and factories profiles that exist only in the branch harness dropped in slice 1. Record those as branch claims, verify master with master's harness plus the ported test, and say plainly which is which in the log.
- 2026-10-15, reconciliation step 4: a slice can be portable in code and unportable in its harness change at the same time. Slice 5's sim, UI, and test applied verbatim (diff stats matched the branch patch exactly), but its tools/balance.js change flips a profile inside a PROFILES table master's harness never had. Check a slice file by file, not as a bundle: port what matches master's structure, and log the rest as not ported with the structural reason, instead of importing a foreign harness to make the patch complete.
- 2026-10-15, payment order fixes may also leave the standard bands untouched: slice 5, like slice 4, changed no number in master's harness output, because master's sensible games end on day 25 before factory upkeep can outrun income. The dedicated order test is the evidence; the bands are only a regression check. Do not read unchanged bands as the slice doing nothing, and do not claim the branch's dramatic band movements (which came from its longer games) for master.
- 2026-10-16, reconciliation step 5: a docs only slice can be the least portable slice in a set, because docs carry numbers. Slice 6's text was mostly branch harness results (200 seed runs, a no factory profile, a click through browser unlock) that master never reproduced. Porting docs verbatim would have laundered branch claims into master's honest list. Rule: every number in a ported doc must trace to a master run in the same step, or the sentence does not come across.
- 2026-10-16, stale taste items are a real defect class: master's DECISIONS_FOR_JASH.md item 1 still quoted Cycle 5 capture days two cycles after they were superseded, and nothing in the test suite can catch that. When a step changes the headline balance numbers, grep the decisions and backlog files for the old numbers in the same step.
- 2026-10-16, Cycle 7 step 1 port: a branch file at a cycle's first commit is not the file the cycle closed with. The branch lore arrived with a gauge contradiction its own judge later fixed in a one line commit (a62608a). Before porting any branch cycle's early step, check for later commits touching the same files inside that cycle and fold their corrections in, naming each fold in the log; otherwise the port knowingly re-ships a flagged defect.
- 2026-10-16, a diff against the branch file at the ported commit isolates interleaved slices for free: diffing master's sim against the branch sim at the Cycle 7 step 1 commit showed exactly three differences (a header wording change, the beat hooks being ported, and the earlier judge flag 1 defender draw block not being ported). That one diff both proved the port's fidelity and surfaced the pending flag 1 item with its exact code location. Use it as the standard fidelity check when a branch commit bundles work from more than one slice.
- 2026-10-16, branch judge flag 1 port: verify a ported test is non vacuous by running the new suite once against the pre port sim in a scratch copy (git show HEAD:js/sim.js into a copied tree). The mirror test failed there and passes on the ported sim, which is stronger evidence than a green suite alone, and it costs one extra test run. Do this for every test that claims to pin a fix.
- 2026-10-16, a documented rule can be only half true in code: Cycle 6 documented that snapshot occupants defend their province even if ordered elsewhere, and master's earlier tests pinned that for the case where the attacker's group sorted first. The asymmetric case (the defender's own attack sorting first) was invisible to those tests because group sort order is by origin province id, which quietly favours the west side. When a rule depends on sort order, test the mirror image, not only the natural case.
- 2026-10-16, Cycle 7 step 2 port: overlapping hunks make per patch insertion sums lie. The four patches applied this run sum to 4 more insertions than the net diff against master, because the judge correction hunks rewrite lines the step itself added. Do not flag that as a fidelity problem or chase it: fetch the branch files at the last folded commit and diff the finished files byte for byte. All four files matched exactly, which settles what patch arithmetic cannot.
- 2026-10-16, a committed browser check can depend on tooling this environment does not have: tools/lore-check.js expects Playwright at paths that do not exist here, while the older tools/browser-check.js drives Chromium over raw CDP and works anywhere. The check still ran at full strength by installing playwright-core into /tmp and pointing PLAYWRIGHT and CHROME at it. Lesson: before declaring a ported check unrunnable, try satisfying its driver from /tmp; and when writing future checks, prefer the raw CDP pattern of browser-check.js so the next environment needs nothing installed.
- 2026-10-16, Cycle 7 step 3 port: a test file can be half portable even when it is a pure append. Four of the branch's six lore tests applied verbatim and passed, but the determinism and zero effect tests drove H.PROFILES.factories, an export only the dropped branch harness has; master's harness exports nothing. Rule: before porting a test append, grep every symbol it uses against master's actual exports, not against the branch's file list. The adaptation kept the branch's intent (full campaign, all three beats, JSON identical with beats off) on a profile master actually has, the passive campaign, and said so in the test itself.
- 2026-10-16, a baseline file is harness output, not prose: the branch baseline is text tables from its six profile harness, so copying it to master would have committed a file no master command can reproduce. Master's baseline is master's own harness output under the same filename and purpose, and its provenance lives in the log and backlog, because one header line inside the file would break the diff it exists for.
- 2026-10-16, a scan that errors is not a scan that passed, again: the repo dash scan first ran a grep pattern this locale rejects (it printed an error and would have looked like zero hits in a pipeline). The byte scan in python (searching the UTF-8 bytes for em and en dashes) is locale proof and is the scan to use in this loop from now on.
- 2026-10-16, Cycle 7 step 4 judge: a fresh judge on master converged independently with the branch judge on the same core findings (the impossible Vessari Drone Gen 2 variant, the lore's implied asymmetries), which is strong evidence those are real and not one judge's taste. Because steps 1 and 2 had folded the branch judge's corrections in early, 6 of its 8 flags were already closed on master and the only fix-now work left was documentation. Lesson: folding a later judge's corrections into an early port pays off twice, once in the port and again at the cycle's own judge.
- 2026-10-16, a variant can be test pinned and still unreachable in play: the suite pins that beats record the first side or both, using staged states, and passes; real campaigns never produce the player Drone Gen 2 variant, because symmetric research accrual plus the AI researching on the first affordable tick caps the player at a day 21 tie. Reachability is a campaign level claim and needs a campaign level tally (this run: 200 passive campaigns, capitalRow enemy 200 of 200, droneGen2 enemy 200 of 200, line3 enemy 198 and player 1). When a step adds content variants, tally which variants real profiles actually fire, and record the unreachable ones in the backlog instead of letting green tests imply they are seen.
- 2026-10-16, record the profile scope with every tally claim: the judge's tallies and the builder's tallies agreed in substance but came from different profiles (a sensible profile that wins by capital capture on day 25 never fires capitalRow at all, while passive fires it by the enemy on day 11). A number without its profile reads as a contradiction later; name the profile in the log entry, as this run did.
- 2026-10-16, judge directed deferral is not a silent carry: the one real code defect this judge found (a staged card and end banner interaction, flag F2) was explicitly assigned to Cycle 8 step 0 by the judge, and the honest move was to write it into BACKLOG.md as a known defect with its reproduction status (judge reproduced in node, 0 natural occurrences in the builder's 200 passive campaigns), not to fix it inside the judge step and not to drop it. A carried defect with a named home step is closed bookkeeping; an unrecorded one is a future surprise.
- 2026-10-16, Cycle 7 step 4 correction: a compressed summary of a judge verdict is not the verdict. This run wrote and pushed its step 4 entry from a summary that garbled the flag list (it invented a card and banner flag, dropped a codex bug entirely, and softened the compass grades), and the full handoff, arriving after the push, required a correction entry, a code fix, and doc corrections across three files. Rule for every future judge step: do not write the log entry, and do not commit anything, until the judge's complete final report is in hand in this context; if a summary arrives first, treat every flag and grade in it as provisional.
- 2026-10-16, state that survives across games must be reset in newGame, every field: the codex kept a turning point selection (codexEntryId) across New Game because newGame reset its sibling fields (shownBeats, cardQueue, pauseBeforeOverlay) and missed this one, and renderCodex trusted the selection against a fresh state.beats. When adding any per game UI state, add its reset to newGame in the same commit, and guard renderers against selections the current game has not produced. The regression shape that pins it (view the thing, New Game, reopen) is Run C of tools/lore-check.js.
- 2026-10-16, Cycle 8 step 0: narrowing a content variant set is only honest when the shipped set is pinned to outcomes, not to intentions. The pin that works is a set equality test: run the real campaign profiles that produce each outcome (passive gives enemy, eager gives both, same seed, public paths only) and assert the produced set equals Object.keys of the shipped variants. A staged test that sets the beat by hand would have passed with the unreachable player text still in the file. Verified non vacuous the usual way: restoring the deleted variant in a scratch copy fails exactly the two new pins.
- 2026-10-16, Cycle 8 step 0: executing a judge prescribed default route is not deciding the underlying taste question. The narrowing changed no balance number and kept the research clock parity, and the log and DECISIONS item 9 both record that the race question stays open and the sim route waits for Jash's word. When a default fires, write the still open question down in the same commit, or a later run will read the shipped default as a settled decision.
- 2026-10-16, Cycle 8 step 1: folding a cycle's judge sim fixes into its step 1 port changes the balance story, and the log must say which numbers belong to which layer. Master's sensible win moved from day 25 to day 46 on 7 seeds with the plain step 1 walls; the branch, with the same folds, recorded its rationed profile at day 46 too. When a port folds later fixes in, compare the result against the branch's post fix numbers, not its step 1 numbers, or a correct port looks like a divergence.
- 2026-10-16, a non enumerable field is how unitStats can serve two consumers honestly: the panels and the pinned stats test see exactly the documented object, while stackPower reads defenseBeforeWalls to apply walls once per stack. If a future change enumerates unitStats (a spread, JSON, or Object.keys in the UI), the field leaks or vanishes silently; grep for defenseBeforeWalls before touching either function.
- 2026-10-16, Cycle 8 step 2: a check whose commit belongs to a later step can still verify the current step without breaking the step boundary: run it from a scratch copy of the whole repo in /tmp (its REPO path resolves relative to its own location, so a lone copy in /tmp fails). The branch's tools/fort-check.js passed 13 of 13 against master's UI this way, and step 3 still has an honest commit to make. Also: the playwright-core module path in this environment is /tmp/pwcore/node_modules/playwright-core, not /tmp/pwcore; requiring the bare directory fails, so use the full module path in PLAYWRIGHT.
- 2026-10-16, Cycle 8 step 3: a prototype harness patch that is never executed looks exactly like a failing profile. The first fortress prototype run "lost 8 of 8" with passive numbers because the patch script sat unrun in /tmp and the harness fell through to tick only for the unknown profile. Rule: before reading any prototype result, grep the patched file for the new code's marker (here __FORTS) and confirm the patch actually landed; a profile name the harness does not dispatch is a silent passive run, not a result.
- 2026-10-16, Cycle 8 step 3: porting a cycle's tests means collecting them from every commit that touched the test file in that cycle's arc, not only the step commit. The step 3 commit held 5 of the 8 fortification tests; the other 3 lived in the judge flag commits after the branch's step 4 (975e8fa, febe7c7), because on the branch those tests were written to pin fixes made after its step 3. Master's fold in step 1 had already absorbed the fixes, so all 8 belong to master's step 3. Count tests per patch (5 plus 2 plus 1) and reconcile against the suite delta (50 to 58; the branch reached 57 because master's step 0 reachability test has no branch counterpart).
- 2026-10-16, Cycle 8 step 3: a fortifying profile can spend real resources and change no outcome, and that is a finding, not a failed profile: fortress ends 800 to 1200 equipment poorer than sensible on every seed and wins on the same day at the same strength, because its walls stand behind the attacking stack. When a profile's spend is invisible in the old report shape, add the spend to the report (here end equipment for both nations) rather than claiming the profile works from its win record alone.
- 2026-10-16, Cycle 8 step 4 judge: the full report rule from the Cycle 7 step 4 correction held this time: nothing was written or committed until the judge subagent's complete report arrived, and the log entry records grades, flags, and the Cycle 9 prescription from that report, not from any interim summary. The verdict converged with the builder's own pre judge verification on every number (suite 58, balance byte identical, browser checks 13, 34, and 6), which is the pattern to keep: builder verifies first, judge independently reruns, and the log cites both.
- 2026-10-16, a browser check can pass every assertion and still miss the combined state next to the ones it tests: fort-check asserted the building badge alone and the finished badge alone, both on top, and the judge caught that together they overlap because both spans share one absolute position. When a UI element has states that can coincide, the check needs the coincident state as its own run (Cycle 9 step 0 adds exactly that), not two single state runs that each pass.
- 2026-10-16, Cycle 8 step 4 judge: a PASS WITH FIX-NOW FLAGS verdict whose judge explicitly assigns the flag to the next cycle's step 0 is closed bookkeeping, not an unfinished step: record the defect in BACKLOG.md with its evidence and exit criteria, name it in the next cycle's step 0, and do not fix it inside the judge step (one step per run) and do not drop it. Same shape as the Cycle 7 F2 carry, applied a second time.
- 2026-10-16, Cycle 9 step 0: a combined state check can contain checks that pass on the pre fix code, and that is fine as long as the defect catching checks are identified honestly. Of the four new combined checks, two (both badge texts present in the tile, the card stating both facts) pass in the mutant with the CSS offset removed, because the spans were always emitted and the card was always right; the two that fail in the mutant (both badges on top, rectangles do not overlap) are the pin. When writing a combined check, run the mutant and say which checks are the pin and which are context, instead of claiming the whole run is non vacuous.
- 2026-10-16, Cycle 9 step 0: the smallest prescribed fix shape held: the judge offered two fix shapes (a CSS offset or merging the spans in renderMap), and the one rule offset closed the flag with no sim or render change, which kept the balance rerun byte identical by construction rather than by luck. When a prescription offers shapes, take the one that touches the fewest surfaces the other exit criteria measure, and say why the other shape was not needed.
- 2026-10-16, Cycle 9 step 1: the branch's cycle numbers are not master's cycle numbers once the two judges diverge. The branch's Cycle 9 is AI decision clock work; master's Cycle 9 is the efficiency ramps its own Cycle 8 judge prescribed. Before assuming a port candidate exists for a cycle, check the branch's commit subjects for that cycle number against master's prescription; when they differ, build fresh against master's prescription and say so in the log, instead of forcing a port or silently skipping the check.
- 2026-10-16, Cycle 9 step 1: an existing suite can silently bound a new system's tuning. The production tests pin that a second unit on one line takes its own full 6 days for the full 60 steel, and that a drone built right after a retool takes exactly 3 days; those pins, plus the step's exit rule that the existing suite stays green before new tests, cap how fast the ramp may rise (rise 2 passes all three with margin; a rise of 5 would still pass the second unit pin but leaves the ramp's early feel to a guess). When a step adds a ramp, simulate its work sums against every timing pin in the suite before choosing the rise, and record which pin is closest to binding.
- 2026-10-16, Cycle 9 step 1: keeping a legacy field's exact meaning (progressDays as funded days on the current unit) while adding the real state beside it (work points) let a 58 test suite pass unmodified through a production model change. The cost is two fields that must be reset together everywhere (completion, retool); grep for every reset site of the old field when adding its sibling, or one path will desync them.
- 2026-10-16, Cycle 9 step 1: a balance movement in opposite directions per seed is not automatically a contradiction to smooth over: sensible moved 3 days earlier on 7 seeds and 3 days later on seed 2024, whose Cycle 8 win was the known outlier. Report the per seed direction and the reason the outlier differs, in the step's own log, rather than quoting only the range; step 3's per seed report against the Cycle 8 baseline is prescribed exactly for this.
- 2026-10-16, Cycle 9 step 2: stage a check's mid build state from a real trajectory, not from convenient numbers. The staged line in tools/efficiency-check.js (work 254, efficiency 130, 2 funded days) is exactly what productionPhase produces when a line starts those days at 126 percent (126 + 128 work, rising to 130); a staged state no real trajectory can reach would let the check's arithmetic pass against a fiction and prove nothing about the panel's live numbers.
- 2026-10-16, Cycle 9 step 2: a warning that exists only when one loss is present will silently miss the quadrant where only the other loss is present. The old retool note showed only with a unit in progress; an idle line at the 150 cap would have lost 50 efficiency points on a retool with no warning at all, the largest single loss the panel owns. When a step extends a warning to a second quantity, enumerate the quadrants (progress or not, ramped or not) and give each a stated sentence, including the two where one side of the loss is zero.
- 2026-10-16, Cycle 9 step 2: when a surface quotes a number that belongs to no particular line (the unit card's build cost), the prescription's name it as base route is the honest one, and it costs one clause. Inventing a representative line for the card would have quoted a live number for a line the player may never use, which is a quieter kind of wrong number.
- 2026-10-16, Cycle 9 step 3: a readout that is exact at the floor and the cap is not exact everywhere between them, and a test that assumed it was would have been a false pin. lineBuildDays is a ceiling at the efficiency the day starts with; at 116 to 119 percent an infantry unit quotes 6 days and is charged 5, because the rising work sums past the need a day early. Rule: when a step pins a charged number equal to a readout, pin equality at the stated points (floor, the staged mid ramp, cap) and pin the documented invariant everywhere else (never longer than the readout), instead of asserting a universal equality the sim never claimed. The sim's own comment already said "this or faster"; reading the comment before writing the pin would have saved the brute force check, though the brute force check is what proved the narrow band's exact edges.
- 2026-10-16, Cycle 9 step 3: a mutant that breaks a shared readout fails every test that reads through it, and that is the honest count to record. The lineWorkPerDay mutant failed 5 of the 7 new tests (60 pass, 5 fail), not only the charged number pin it was aimed at, because the rise and retool tests assert work amounts from the same function. The surgical parity mutant (rise only for the player) failed exactly 1. Record both shapes as measured and say which prescribed pin each mutant was aimed at; do not trim assertions from tests just to make a mutant's failure count look surgical.
- 2026-10-16, Cycle 9 step 3: a prescribed "revisit the question" item is also a contradiction hunt. The backlog's economy item still stated, a full cycle after fortifications shipped, that factory construction was equipment's only spend and that the one more cycle clock was still running. Nothing in the suite can catch a stale sentence like that; when a step revisits a question, grep the docs for the question's old answer and correct it in the same commit, the same rule the stale taste item lesson set for old numbers, now applied to old claims.
- 2026-10-16, Cycle 9 step 4 judge: the full report rule held for the third judge running. Nothing was written or committed until the judge subagent's complete report arrived, and its verdict, grades, and prescription were checkable against the builder's own pre judge verification, which had run first and matched on every number (suite 65, balance byte identical, browser checks 15, 17, 34, 6). Keep that order exactly: builder verifies first, judge independently reruns, the log cites both, and a judge that reproduces the step's own mutants and trace itself (this one reproduced both step 3 mutants and the seed 42 trace) is worth more than one that only reads the log.
- 2026-10-16, Cycle 9 step 4 judge: a quote can be safe and still be wrong. lineBuildDays never understates (a ceiling, pinned at every efficiency), and the step 3 finding treated that as acceptable; the judge ruled the ceiling semantics live in a code comment the player never sees, while the efficiency row states the ceiling as fact and at 118 percent reads 6 days against a base of 6, hiding a real 5 day charge. Lesson: judge every on screen number by what its surface claims, not by what the code comment knows; a conservative number stated as exact is a legibility defect when making it exact is cheap and touches no charge path. The prescribed fix shape is the honest one: iterate the documented rise inside the readout so the quote matches the existing charge, never slow the charge to match the quote.
- 2026-10-16, a presentation derivation from a shared readout is not a second computation: fundedDaysToCap in js/main.js survived the one function audit because its only inputs are the readout itself plus CFG constants, nothing charges from it, and the step that built it was prescribed to display exactly that number. When auditing a one function claim, trace what a derived number feeds, not only where it is computed; a display that feeds nothing is presentation, a display that feeds a charge would be a bypass.
- 2026-10-16, Cycle 10 step 0: repinning a test from a weaker invariant to equality does not by itself prove the fix landed, because the old test also passes on the new code. The evidence is the scratch run of the repinned test against the pre fix code (here exactly 1 fail, 64 pass, the band assertion), same non vacuity pattern as every earlier port, now applied to a repin. Do both runs every time a test's claim is strengthened.
- 2026-10-16, Cycle 10 step 0: making a readout exact by iterating the process it quotes (same rise, same cap, same order: add work, then rise) removes a whole class of band defects at once: the former 116 to 119 band, and any future band a ceiling would create if tuning changes the rise, are exact by construction because quote and charge run the same sum. When a quote and a charge disagree in a narrow band, align the quote to the charge's iteration rather than patching the band.
- 2026-10-16, Cycle 10 step 1: for recurring content, reachability and frequency are both shipping criteria and only a tally measures either. The prototype (hooks for seven candidate facts, four harness profiles, 8 seeds, 32 campaigns) killed the most narratively obvious candidate (a province retaken: 0 occurrences in 32 campaigns) and the most available ones (new rail completed up to 23 per campaign, units completed up to 40), and left exactly the three occasional facts that shipped. Run the candidate tally before writing any variant text; text written first would have anchored the choice.
- 2026-10-16, Cycle 10 step 1: transient facts cannot be recorded by an end of tick predicate phase the way the beats are, because a completion or a crossing leaves no persistent predicate to count exactly. Record at the event site through one helper with one state field and a CFG off switch in the campaignBeats pattern, and prove by grep that no rule reads the field. The beatPhase guarantee is about readership, not about where the write happens.
- 2026-10-16, Cycle 10 step 1: a tally's counts can be completely seed uniform (every seed gave identical texture counts per profile) because scripted profiles dominate seed variation; report the uniformity as measured instead of implying seed diversity, and name which profile proves which variant, especially when the prescribed minimum scope (passive and sensible) proves only five of six variants and the sixth belongs to the profile built for it (fortress, for player walls).
- 2026-10-16, Cycle 10 step 2: a check's burst window must be sized against the game's tick, not against feel. At speed 2 a game day is 300 ms, so a 600 ms no card window is exactly two days and intermittently merged the day 19 and day 21 tick groups, which sent Run B draining to the campaign end and timing out twice before the cause was visible in its own log (burst 2 contained five cards from two ticks). Queued cards appear synchronously on Continue, so the correct window is the smallest that detects a synchronous appearance (150 ms), and the safety margin is measured in game days to the next possible card (at least 2 days, 600 ms). When a browser check flakes intermittently, read its log for a merged or split group before blaming the game.
- 2026-10-16, Cycle 10 step 2: a running check that reads two page facts in two separate round trips (day counter, then pause button text) can fail honestly while the game is right: the war resumed after the codex, advanced into the next card, and re-paused before the second read landed. Assert the fact that proves the claim with the fewest reads (day advance for resumption, when pause restoration is already pinned by dedicated checks nearby), and write the reason into the check's comment and the log instead of quietly widening the assertion.
- 2026-10-16, Cycle 10 step 2: ordering cards within a tick by when their facts happen (textures during the phases, beats at the end of the tick) made the browser timeline match the sim timeline with no extra state: the queue order is the record order, and the occurrence count is derivable at queue time from the records themselves (same id, same side, up to and including the record). When a UI needs a count or an order for recorded facts, derive it from the records at display time rather than storing a second copy that can drift.
- 2026-10-16, Cycle 10 step 3: a test file that needs a harness profile should adapt the harness script into the test file and say so in its header, rather than requiring the harness: tools/balance.js runs on load and exports nothing, so requiring it would execute all four profiles as a load side effect. The adaptation (about 90 lines, public commands only) kept the suite self contained; the whole suite including three full campaigns in the variant pin runs in about a second.
- 2026-10-16, Cycle 10 step 3: the cleanest non vacuity mutant is one line inside the one helper every recording passes through. recordTexture plus 1 steel to the recording nation failed exactly the zero effect test (72 pass, 1 fail) because every other new pin measures days, sides, counts, or determinism between equally treated runs, none of which a steel drip moves. When a mutant fails exactly its target, that is evidence the test pins the claim rather than the implementation; design the mutant at the choke point, not at a call site.
- 2026-10-16, Cycle 10 step 3: /tmp does not persist between runs in this environment (the playwright-core install from earlier runs was gone at browser check time). Reinstalling it into /tmp/pwcore took seconds and the checks ran at full strength; do not treat a missing /tmp install as a check failure, and do not commit around it.
- 2026-10-16, Cycle 10 step 4 judge: the full report rule held for the fourth judge running and produced the loop's first clean PASS with no fix-now flags. The deciding pattern is now confirmed across four judges: builder verifies first on every prescribed number, the judge independently reruns (this one reproduced the step 3 steel mutant at exactly 72 pass and 1 fail, rebuilt the reachability tally across 32 campaigns, and ran the on and off comparison on a second profile the formal test does not pin), and the log cites both runs.
